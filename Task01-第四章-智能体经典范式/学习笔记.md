## 一、ReAct 范式：思考与行动相辅相成

### 1. 核心理念与运作循环
- **核心思想**：**Reasoning and Acting**。智能体不是盲目行动，也不是纸上谈兵，而是将“内部推理”与“外部行动”紧密结合。
- **三大规范要素**：
  - `Thought`（思考）：分析当前处境、拆解阶段目标、评估可用资源；
  - `Action`（行动）：决定调用什么外部工具及传入什么参数，或在收集完毕后给出 `Finish`；
  - `Observation`（观测）：执行工具后从真实世界获取的环境反馈。
- **经典轮转闭环**：  
  $$\text{Thought} \longrightarrow \text{Action} \longrightarrow \text{Observation} \longrightarrow \text{Thought} \dots$$

### 2. 工具调用机制（Tool Call）的解耦实现
智能体并非生来就会用工具，需要宿主代码搭建标准交互桥梁：
1. **实现具体工具的核心逻辑**：定义具有确定输入输出的函数（如基于 SerpApi/Tavily 的搜索引擎、计算器等）；
2. **构建通用的工具执行器（`ToolExecutor` 类）**：
   - 统一管理、注册工具元数据（工具名称、功能描述文本、函数引用）；
   - 提供动态的格式化接口，用于将可用工具列表自动生成文本注入到 System Prompt；
3. **工具执行与调度**：根据解析出的工具名称动态派发调用。

### 3. `ReActAgent` 智能体的工程组装
将大模型客户端（`HelloAgentsLLM`）与工具执行器（`ToolExecutor`）组装为统一的类：
1. **系统提示词设计（Prompt Template）**：设计标准化插槽，动态注入：
   - 当前可调用的工具清单及参数格式规范；
   - 用户的原始任务目标；
   - 前序轮次的 `Action` 与 `Observation` 交互历史。
2. **核心执行循环与安全边界**：
   - **`max_steps`（最长步长）**：作为至关重要的安全防护参数，强制限制最大循环次数，防止智能体在特定歧义问题下陷入无限循环。
3. **输出解析器（Output Parser）**：
   - 从模型吐出的纯文本中提取 `Thought` 与 `Action` 字段；
   - 可借助正则表达式辅助解析（注意边界格式漂移处理）。
4. **工具调用与执行**：提取工具名与入参，交由 `ToolExecutor` 执行，捕获异常并转化为文本。
5. **观测结果整合（形成闭环）**：
   - **最关键的一步**：将当前轮次的 `Action` 以及工具返回的 `Observation` 追加回上下文历史中，作为新记忆喂给下一轮模型思考。
6. **运行实例与分析**：
   - 测试“华为最新手机及其主要卖点”等实时检索任务，观察模型如何先搜索、再阅读、最后总结输出。

> ⚠️ **ReAct 的核心局限**：  
> 具有明显的“步进式（Step-by-step）局部贪心”特征，缺乏对长链路复杂任务的宏观前瞻视野，容易“只见树木不见森林”。由此自然引出第二种范式——**Plan-and-Solve**。

## 二、Plan-and-Solve 范式：谋定而后动

### 1. 核心理念
- **核心思想**：针对复杂长流程任务，借鉴人类“先规划、后执行”的思维习惯，将**宏观规划（Planning）**与**微观执行（Solving）**显式拆解为两个解耦的阶段。

### 2. 双组件架构
1. **规划器（Planner）**：
   - **职责**：只负责统揽全局，将大任务拆解为一个逻辑严密的子任务列表；
   - **输出约束**：通过提示词强约束，令模型仅输出纯净的结构化数据（如 Python List `["步骤1", "步骤2", ...]`），便于程序代码解析。
2. **执行器（Executor / Solver）**：
   - **职责**：不操心全局蓝图，专注当下单一步骤的计算与落地；
   - **上下文递进**：每一步执行时，只输入“原始问题 + 完整规划清单 + 前序已完成步骤及答案 + 当前步骤”，避免上下文噪声。

### 3. 运行实例与优势
- **实战案例**：水果店多日苹果买卖数量推理题。
- **优势体现**：步骤条理极为清晰，极大降低了大模型一步到位的认知计算负荷，大幅减少中间运算跳步或逻辑断裂。

> ⚠️ **Plan-and-Solve 的核心局限**：  
> 规划属于“静态前置规划”。如果在中间步骤遇到外部依赖不可达、参数失效或预期偏差，缺乏即时调整能力。如果前序步骤输出错误，后续步骤容易产生**级联雪崩**（由此在工程上催生了动态重规划 Dynamic Re-planning）。

## 三、Reflection 范式：自我审视与迭代进化

### 1. 核心理念
- **核心思想**：模拟人类创作者“草稿 ➔ 自我审校 ➔ 精修重构”的高阶心智过程。大模型的首次单次生成（Zero-shot）往往存在浅层漏洞或非最优解，通过赋予其“自省（Self-Reflect）”能力来逼近质量上限。

### 2. 核心架构与角色流转
1. **记忆模块（Memory）**：
   - 追踪存储完整的演进轨迹，区分记录执行产物（Execution）与评审反馈（Reflection）。
2. **多重角色演进回路**：
   - **初始生成（Actor）**：产出初始版本（如编写基础的 Python 质数筛选函数）；
   - **反思挑刺（Evaluator）**：换位为“严格的代码评审员/审查官”，从算法渐近复杂度、极端边界条件、内存瓶颈等维度深入剖析缺陷；
   - **优化重写（Refiner）**：结合评审员具体的批评清单，进行代码重构与升级；
   - **终止机制**：评委反馈无改进空间或达到最大迭代轮次时，主动停止并交付最终版本。

### 3. 实战案例表现
- 质数筛选任务中，初始埃氏筛法 $O(n \log \log n)$ 经反思模型识别出“重复标记合数”的瓶颈后，自动重构进化为 $O(n)$ 线性欧拉筛并引入 `bytearray` 优化内存，直观体现了自省机制的威力。

> ⚠️ **Reflection 的核心代价**：  
> Token 消耗与推理延迟成倍激增，适合对输出质量要求极高的非实时场景（如代码重构、合同审查、深度研究写作）。

## 四、三大经典范式横向对比与选型指南

| 维度 | ReAct | Plan-and-Solve | Reflection |
| :--- | :--- | :--- | :--- |
| **思维机制** | 边想边做，即时反馈驱动 | 宏观规划先行，逐步落实 | 先做再审，多轮迭代优化 |
| **工具依赖度** | 极高（核心就是与外部环境交互） | 中等（规划和求解可按需接工具） | 较低（主要依赖模型自身的推理与批评能力） |
| **核心优势** | 动态适应力强，环境容错高 | 擅长长链路逻辑，不易中途迷路 | 输出质量天花板高，能剔除浅层缺陷 |
| **主要代价** | 容易陷入局部细节死循环 | 静态规划缺乏变通弹性 | Token 开销大，响应延迟高 |
| **典型适用场景** | 实时问答、智能客服、设备控制 | 复杂应用题、报表流水线、多步迁移 | 代码自动编写、论文润色、逻辑严密审查 |
